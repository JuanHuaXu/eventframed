# Immutable norm reuse: performance screen FAILED

The candidate stores squared norm during existing record validation, uses the
original dot-product order and sqrt(aa*bb), and clears derived state from Lookup
values. PrepareLayered recomputes it from edited vectors, ignoring supplied
cached state. No mutable/unbounded map cache is added.

Bitwise scalar cosine tests across dimensions 1/2/17/768/4096 and varied scales,
stale-norm edits, and all 16 insertion + 16 deletion graph captures passed under
race detection (55.822s). Ordinary researchindex tests passed (5.206s).

Measured allocation is unchanged despite the added float64 field, consistent
with allocation-size rounding, not proof that retained logical storage is free.

Control source is archived in norm-baseline; its benchmark overlay excludes only
the new norm-specific test which cannot compile against the old record shape.
The same benchmark and captures are used. Raw outputs: norm-control-cost.jsonl,
norm-candidate-cost.jsonl; structured comparison: norm-cost-comparison.json,
generated by check-norm-cost.mjs. Ordered control-then-candidate arms do not
establish temporal robustness. No fresh confirmation or load rescue is claimed.

The current research implementation contains the candidate for subsequent
controlled composition, not production adoption. This small gain alone cannot
offset the roughly 4ms per-write persistence cost observed under load. Next lead:
bounded group commit with atomic ordered revision publication, preserving
deadline and failure semantics. Archive/control remains available; do not call
the failed norm screen a successful rescue.
